# Stage 10B-2: 任务树架构重设计 — 问题清单

## 背景

当前架构：领域 = 状态容器（conversation + 状态）
目标架构：领域 = 无状态标签，任务树 = 状态载体

核心概念：
- **TaskNode** = 存储概念（磁盘上的实体集合：对话、资源、结论、推理记录）
- **TaskThread** = 运行时概念（内存中加载 TaskNode 的部分内容执行，同时只有一个）
- **领域** = 无状态标签，提供共享上下文（资源索引、规则），不持有 conversation
- **守护意识** 判断"继续已有任务（加载 TaskNode 到 TaskThread）" vs "新建任务"

---

## 问题 1：任务生命周期 ✅ 已回答

TaskNode 是存储概念，TaskThread 是运行时概念。类似 OS 进程映像 vs 正在执行的进程。

- **Q1a**: 什么时候算"完成"？用户说"谢谢"不代表结束，但可能代表结束。执行意识是否有主动声明完成的机制？
  - ✅ 没有明显完成界线。TaskThread 有状态（running/suspended），TaskNode 本身无状态（只是磁盘上的实体集合）。切换到其它 task 时，当前 task 保存到磁盘（不激活/挂起），需要时再恢复。
- **Q1b**: 什么时候"过期"？用户聊了 10 轮任务 A，切到任务 B，隔 20 轮后回来聊 A——A 的 conversation 还保留吗？
  - ✅ 磁盘保存，理论上不过期。后续可能加时间相关的过期限制。
- **Q1c**: 并发活跃任务数量上限？A 和 B 同时活跃，守护意识维护所有活跃任务的状态，是否需要限制？
  - ✅ 不存在并发。TaskNode 不激活就处于离线磁盘状态。每次只有一个 TaskThread 运行（单线程）。

## 问题 2：守护意识的路由负担 ✅ 已回答

当前守护意识只判断领域（粗粒度），新架构要判断任务归属（细粒度）。

**核心认知**：memory 实体组成的任务场景镜像树 = 对话的全量 context。守护意识和执行意识只是这棵镜像树上游历的蚂蚁。守护意识的真正功能不只是分配任务，而是依托实体镜像树产生自我意识（我是谁、我在哪里、我的历史是什么、我正在做什么），在对全量实体树有针对性摘要的基础上，正确指导执行意识去做具体任务。类似公司治理——董事会持有全局信息做决策，不与执行部门争权。

- **Q2a**: "改进帆船"属于 T1（3D场景开发）还是新建 T2？判断依据是什么？
  - ✅ 判断依据：1. 领域（用户新请求的路由）2. 执行意识 spawn_task（子任务派生后的 dispatch）。
- **Q2b**: 守护意识看不到任务内部完整对话，只有任务描述和摘要，信息是否足够？
  - ✅ 足够。守护意识持有全局信息，细节是执行意识的事。所有关键实体都会记录，执行意识处理不了还有上升措施（escalate）。
- **Q2c**: 判断错误的后果——把本应新开任务的消息塞进旧任务，会污染 conversation，如何补救？
  - ✅ 守护意识持有全量实体信息，领域分配出错可能性低。即使出错，执行意识有边界判断（escalate），所有关键实体都会记录，不会丢失。

**衍生思考（待定）：**
- **Q2-D1**: 实体模型是否足够？守护意识需要感知任务树结构、任务摘要，当前 analyze_turn 产出的实体（domain_task/subtask/analysis/rule/resource）可能无法高效组装出任务树全貌。是否需要新的实体类型或摘要机制？
  - ✅ domain_task 和 subtask 合并为 taskNode。
- **Q2-D2**: 两条 dispatch 路径（领域路由 vs spawn 路由）语义完全不同，当前 dispatch_task 混在一起处理，新架构下是否需要拆分？
- **Q2-D3**: 实体树持久化后会膨胀，守护意识不可能每次遍历全量实体做路由。是否需要分层摘要机制（顶层：活跃任务列表+领域概览 / 中层：任务摘要 / 底层：完整实体）？摘要是静态产出还是动态组装？

## 问题 3：dispatch_task 的"继续"vs"新建"

当前 dispatch_task 是"找领域子意识→激活或创建"。新架构要分两条路径。

- **Q3a**: 继续已有任务时，system prompt 可能过时（规则变了、资源更新了），是重建 prompt 还是保留旧 prompt？
- **Q3b**: 新建任务时，需要组装全新的执行纲领 + 资源索引，和当前逻辑类似。但继续任务时，新的用户消息怎么注入——直接追加到 conversation，还是需要特殊处理？

## 问题 4：资源归属

当前资源实体关联到 subtask。新架构下同领域多任务并存。

- **Q4a**: T1 发现的资源 T2 应该能看到吗？（通过领域共享）
- **Q4b**: T1 的中间结论（非资源实体）T2 看不到，spawn 时是否需要显式传递？
- **Q4c**: indexer 记录的资源归属领域还是任务？归属领域的话，T2 可能看到不相关的资源。

## 问题 5：spawn 深度链的上下文传递

T1 → spawn → T2 → spawn → T3，每一层 resume 注入子结果。

- **Q5a**: T1 在 suspended 期间，领域资源索引被 T2/T3 更新了。T1 resume 时是否需要刷新资源索引？
- **Q5b**: 多层 resume 后，conversation 可能膨胀到超出上下文窗口。是否需要压缩机制？

## 问题 6：核心断点 — 守护意识路由信息不足

守护意识要决定消息归属哪个任务，但只看得到任务描述和 analyze_turn 摘要，看不到完整对话。

- **Q6a**: 仅靠摘要能否准确判断任务归属？
- **Q6b**: 活跃任务多了（3+），路由准确率是否下降？是否需要给守护意识更多上下文（如最近 N 轮对话摘要）？
- **Q6c**: 是否需要引入"显式任务切换"机制——用户主动说"切换到任务 A"？
